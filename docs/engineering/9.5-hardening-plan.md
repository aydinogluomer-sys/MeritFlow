# MeritFlow — Engineering 9.5 Hardening Implementation Plan

> **Amaç:** MeritFlow'u yeni feature ekleyerek değil, mevcut mimarinin
correctness, security, determinism, test depth, CI enforceability ve
failure-mode dayanıklılığını kanıtlayarak **repo/code mühendisliğinde ortalama
9.5/10** seviyesine çıkarmak.
>
> **Kapsam:** Bu dosya öncelikle repository/code engineering içindir. Gerçek
production deployment, PITR kanıtı, gerçek alert firing, gerçek credential
rotation ve production incident drill gibi operasyonel kanıtlar ayrı bir
“operational proof” katmanıdır. Bu rehber onların kod-side enabler'larını
hazırlayabilir ama production erişimi olmadan “kanıtlandı” saymaz.
>
> **Prensip:** MeritFlow'un PostgreSQL + Supabase + Next.js modular-monolith
omurgası korunacak. Microservice, Kafka, Kubernetes, event sourcing, gereksiz
Redis/KV veya sırf “enterprise görünmek” için altyapı eklenmeyecek.
>
> **Başlangıç repo gerçekliği:** Projede Next.js 16 / React 19 / Supabase /
TypeScript / Vitest / Playwright var; CI'da lint, typecheck, unit, migration
lint, pgTAP, build ve E2E işleri bulunuyor. Financial invariants, RLS, ledger,
reconciliation, outbox ve typed-error katmanları önemli ölçüde mevcut. Bu plan,
kalan correctness boşluklarını kapatır.

## 2. ENGINEERING-13 — Performance Gate'i Gerçek Hale Getir

## Problem

Mevcut benchmark scriptindeki `printf ... | python3 - <<'PY'` tipi stdin
kullanımı, pipe'taki EXPLAIN JSON'u Python parser'a vermek yerine here-doc'un
stdin'i ele geçirmesine yol açabilir. CI logunda `p50=0.00ms` ve broken-pipe
görülmesi false-green ihtimalini kanıtlar.

**Bu düzeltilmeden perf-smoke güvenilir bir gate değildir.**

## Hedef mimari

```text
PostgreSQL
  │
  ├─ EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
  ▼
scripts/perf/parse-explain.js
  │
  ├─ execution time
  ├─ node tree
  ├─ Seq Scan list
  ├─ actual rows
  └─ buffers
  ▼
benchmark aggregator
  │
  ├─ p50
  ├─ p95
  ├─ p99
  └─ structural regressions
  ▼
CI PASS / FAIL
```

## Dosyalar

```text
scripts/perf-benchmark.sh
scripts/perf/parse-explain.js
scripts/perf/calc-percentiles.js
tests/fixtures/perf/
  indexed-query.json
  seq-scan-large.json
  nested-plan.json
  empty-plan.json
scripts/perf-selftest.sh
.github/workflows/ci.yml
docs/runbooks/performance.md
```

## Uygulama

## A. Parser'ı shell heredoc'tan ayır

`parse-explain.js`:

- stdin'den JSON okur.
- JSON parse hatasında exit 2.
- `Execution Time` yoksa exit 3.
- bütün plan tree recursive taranır.
- `Seq Scan` node'ları relation + actual rows ile çıkarılır.
- stdout yalnız machine-readable JSON olsun.

Örnek çıktı:

```json
{
  "executionMs": 3.21,
  "seqScans": [
    { "relation": "tasks", "actualRows": 14000 }
  ],
  "sharedHitBlocks": 923
}
```

## B. Percentile parser ayrı olsun

`calc-percentiles.js`:

- stdin'den newline separated number alır.
- boş input PASS etmez.
- NaN PASS etmez.
- p50/p95/p99 üretir.

## C. Self-test

`bash scripts/perf-selftest.sh`:

```text
indexed fixture -> seqScanCount 0
large seq scan fixture -> seqScanCount >=1
invalid JSON -> non-zero exit
empty timings -> non-zero exit
known [1,2,3,4,5] -> deterministic percentile
```

## D. Mutant/proof test

CI'da veya local proof'ta selective query index'i test DB'de geçici olarak
düşür. Benchmark **kırmızı** olmalı. Sonra DB reset.

Bu proof dokümana kaydedilmeli:

```text
Injected regression: selective tasks query forced to seq scan
Expected: perf-smoke FAIL
Observed: FAIL
```

Bu yapılmadan ENGINEERING-13 kapanmaz.

## E. Timing budget stratejisi

İlk doğru ölçümden önce keyfi absolute ms threshold yazma.

İlk stabil CI history'den baseline çıkar. İlk politika:

```text
p95 > baseline * 1.30 -> warning
p95 > baseline * 1.50 -> fail
```

CI noise fazlaysa structural query-plan gate'i timing'den daha güçlü kabul et.

## F. Benchmark kapsamı

- task list
- point ledger summary
- leaderboard
- finance payout view
- finance totals

- dispute queue

Write/RPC:

Profiles:


## 3. ENGINEERING-14 — Canonical Tenant Context

## Problem (2)

Application tarafında aktif org cookie ile seçiliyor. DB `current_org()` ise
request-level active org bağlanmadığında ilk aktif membership'e fallback
edebiliyor. Multi-org kullanıcıda application ve RLS tenant'ı farklı olmamalı.

## Bağlayıcı prensip

> **Bir request içindeki application authorization context ve PostgreSQL RLS
tenant context aynı organization id'yi kullanmalıdır.**

## Hedef

```text
Cookie / user selection
    │
    ▼
getActiveOrg()
    │ membership doğrula
    ▼
ActiveOrgContext { organizationId, profileId, role }
    │
    ├───────────────┐
    ▼               ▼
requirePermission   Supabase request header
                    x-meritflow-org-id
                         │
                         ▼
                    PostgREST request.headers
                         │
                         ▼
                    current_org()
                         │
                    membership doğrula
                         ▼
                         RLS
```

PostgREST request header'ları DB transaction-scoped request context'inden
okunabilir; Supabase JS custom headers gönderebilir. Ancak **header
authorization kaynağı değildir**: DB membership'i doğrular.

## Dosyalar (2)

```text

```

## A. Typed context

```ts

```

## B. Tenant-aware server client

`createTenantClient(activeOrgId)` custom header ekler:


## C. `current_org()` revizyonu

Yeni migration:
